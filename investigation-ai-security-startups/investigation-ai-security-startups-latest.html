一封邮件，三种不同的阻断位置

分析场景，未实测。合法任务是读供应商邮件、查询采购状态、草拟回复；攻击者试图让agent读取秘密并向外部地址发送。

选择要叠加的控制条件

默认：仅内容detector。以下是条件推演，没有概率或产品实测结果。

不增加这三类控制

如果agent服从邮件中的恶意指令，且继承的数据库与邮件凭证允许读取和发送，就存在外泄路径。模型是否服从注入仍是变量；本例没有测量成功率。

验收重点：默认允许的工具能力大于“草拟回复”所需能力。

仅内容detector

在邮件进入上下文前检查。命中规则或分类器时可阻断；漏检时，原有读表与外发路径仍在。对正常长邮件误报也可能打断合法任务。

验收重点：检测“像不像攻击”没有改变动作授权。

仅轨迹/工具策略

假设所有相关tool calls均受中介：识别“读敏感表→向未批准目的地发送”的组合，在发送前拒绝。邮件是否被detector识别不影响这条规则。

验收重点：遗漏hook、标签或历史状态，或策略无法表达业务例外，都会改变结果。

detector＋轨迹策略

先减少恶意内容进入上下文，再于工具执行前检查敏感读取与外发关系。detector漏检时仍有执行约束；规则漏覆盖时detector仍只提供概率性帮助。

验收重点：覆盖和策略质量决定组合效果；不能把两个宣传指标直接相乘。

仅身份/凭证约束

按合法任务只授予采购状态查询和草稿创建权限，不授予send动作，示例的实际外发被阻断。如果业务确需发送邮件，身份有效仍不说明目的地和内容被允许。

验收重点：最小权限与短时凭证缩小可执行范围；需验证权限是否确实由目标系统执行。

detector＋身份约束

内容检查降低被注入的机会；即使漏检，草稿任务的身份没有send权限。若后续业务扩大授权，必须重新检查新增的数据与输出路径。

验收重点：这是限定任务和权限下的分析，不能泛化为所有邮件agent安全。

轨迹策略＋身份约束

凭证先限制资源与动作，策略再检查被允许动作的上下文、历史和目的地。对确需发送的其他任务，可把允许身份与允许流向分别验收。

验收重点：策略引擎必须看到实际动作，凭证不能被旁路工具替换。

三类控制组合

内容检查、执行前轨迹策略、最小权限各负责一层；在本例假设下形成互补。仍需测试间接渠道、派生敏感数据、合法例外、误报与任务完成率。

验收重点：组合不是无条件保证；本页没有运行或测试任何厂商产品。

把行业观察转成可测的问题

下面是候选研究和创业验证问题，尚未做完整的新颖性审查。先选择一个真实工作流，再确定技术手段。

  1. 任务授权，能否成为可执行且可撤销的边界？

    身份图回答“有什么权限”；用户任务还涉及“为什么、何时、为谁”。把任务、委托、资源和外发目的地串成一条可审计链。

    观察对象Invariant / Zenity / Astrix / Token / Oasis应测证据合法任务效用、越权阻断、撤销与旁路首要取舍策略维护和完整中介成本

  2. 安全发现，能否到达修复验收？

    区分候选、历史重现、盲测新发现、客户环境验证与补丁验收。把PoC、去重、补丁、回归和开发者接受绑定起来。

    观察对象XBOW / RunSybil / AISLE / Escape / Aikido应测证据有效PoC、失败分布、修复后复测与成本首要取舍真实目标、状态副作用及披露约束

  3. SOC agent，能否把“未知”保留到结案？

    攻击者可能污染日志字段、邮件和工具返回。将查询正确性、证据完整性与响应安全性分别评估，避免把流畅报告误当正确调查。

    观察对象Dropzone / Prophet / 7AI / Simbian / Torq应测证据误结案、人工重开、工具错误与污染回放首要取舍吞吐、遥测质量与误操作代价

  4. 私有部署和模型压缩，牺牲了哪些长尾能力？

    以Aikido Altar为例：公开32个已知CVE的定向重发现实验可以启发测试，但不能替代新漏洞探索或完整修复评测。

    观察对象本地模型 / 私有客户环境 / 领域评测应测证据长程工具链、稀有类别、同任务成本首要取舍数据驻留、硬件成本与尾部失败

    Altar公开实验及范围

职业选择按实际工作内容判断：评测团队重攻击与测量；行动/身份团队重系统与企业接口；漏洞团队重探索和验证；SOC团队重数据、调查与交付。被收购团队应重新核对研究发表与产品路线。

创业验证先回答：谁有损失和预算、现有控制点为何接不住、客户如何验收、数据与权限如何取得。先用具体设计伙伴和付费试点检验需求。
